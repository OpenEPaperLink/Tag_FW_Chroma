# G5 images on Chroma

Firmware version `0x0016` accepts `DATATYPE_IMG_G5` (`0x31`) in addition to the existing raw image types. The decoder stores two packed rows instead of transition arrays. It streams compressed bytes from EEPROM into an erased raw-image slot, then uses the existing display, overlay and custom-screen paths.

## File and cache behavior

The six-byte header is `[6, width_lo, width_hi, height_lo, height_hi, planes]`. Dimensions are physical: 128×296 on Chroma29, 400×300 on Chroma42, 600×448 on Chroma60, and 640×384 on Chroma74. Plane count is one or two. Two planes are one continuous G5 stream with twice the height; the reference row is preserved across the plane boundary. Decoded bytes retain their original polarity and order.

The compressed file must fit an image slot after its 22-byte EEPROM image header. G5 needs two writable image slots during conversion, excluding the currently displayed image and protected special preloads. If those slots are unavailable, or validation/decoding fails, the transfer is not acknowledged as complete. The compressed source never gets a valid image header. The destination becomes valid only after all rows and header metadata have been programmed; a separate final write publishes the valid marker.

Special status-screen preloads are replaced after the new raw image is committed. Multiple slideshow preloads remain separate. The raw cache retains the compressed transfer's version and argument so repeated availability announcements reuse the decoded image. Preload cache hits require the exact argument, finish any interrupted special-image cleanup, and preserve unrelated pending transfers. Raw image handling and OTA staging remain separate from the decoder workspace.

## RAM and flash

The existing 2,083-byte transfer buffer is a union with a 384-byte G5 workspace: two 80-byte rows, three 32-byte state/work/transfer regions, and a 128-byte input cache. There is no heap allocation or additional frame buffer. The decoder is non-reentrant and runs only after downloading has finished. Slot/header helpers must not use this shared buffer during decoding.

Chroma60 raw two-plane output is 67,200 bytes; image sizes and EEPROM addresses remain 32-bit. NOR writes wait for the final page program before returning, allowing the next compressed-source refill or metadata read safely.

The supporting size changes retain release behavior: explicit XDATA pointer targets, omitted unused release helper bodies, lossless font-column sharing, compact code-memory LUT descriptors, equivalent pixel output, shared full/short check-in logic and CRC32 arithmetic, and the existing formatter's pointer-to-number mode for MAC strings. Fonts, logos, UART diagnostics, barcodes on supported boards, settings, commands and OTA remain enabled.

## AP configuration

The AP selects G5 by tag-type metadata and minimum software version. After validating the firmware on the intended hardware, set the relevant AP tag type's `g5` minimum to **22 decimal** (`0x0016`). Tags running older firmware must continue receiving raw images. This PR does not change the AP repository or published binaries.

Do not enable the generic zlib compression capability bit: it advertises a different decoder. The AP must retain raw fallback for incompressible images and encoder flip-limit failures. AP encoder versions whose buffer-size arguments are 16-bit also need a separate fix to compress Chroma60's complete two-plane image; raw fallback remains usable.

## Validation

Run the production decoder tests and protocol/storage tests from the repository root:

```sh
python3 tests/packed_g5/run_tests.py --sanitize
python3 tests/packed_g5/test_storage.py
```

The suite includes independently generated streams, frozen AP interoperability fixtures, exhaustive small rows, all coding modes, dense 600/640-pixel rows, both planes, bounded NOR refills/writes, malformed/truncated files, and sanitizer checks. The storage suite exercises the production allocation/commit/acknowledgement code and NOR readiness behavior. No sibling repositories or third-party encoder sources are required.

Build all seven variants with the repository-supported SDCC 4.2.0:

```sh
cd Chroma_Tag_FW/OEPL
for build in chroma29 chroma29_8151 chroma42 chroma42_8176 chroma60 chroma74r chroma74y; do
    make BUILD="$build"
done
```

Host tests, builds and simulator checks do not qualify real hardware timing, power use or interruption recovery. Before publishing binaries, verify both display passes, custom/slideshow preloads, failed and resumed transfers, low-battery/no-RF overlays, EEPROM page boundaries, reboot recovery and OTA on each controller variant. The PR supplies source and tests, not prebuilt release images.
